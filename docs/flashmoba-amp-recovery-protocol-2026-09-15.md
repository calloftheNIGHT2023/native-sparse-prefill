# AMP质量恢复试验：先冻结，再租卡

## 要回答的问题

目前只知道长输入能够加速，尚不知道训练后能否保住质量。本轮检验：在相同16K输入、相同token预算和相同学习率搜索次数下，密集、K4、K16各自最好的校准配置，是否能兼顾语言建模损失和实际训练耗时。

这是密集预训练Qwen2.5-0.5B的LoRA适配可行性试验，不是从头原生稀疏预训练，不把现成稀疏算子的加速作为原创贡献。成功才有理由进一步研究适配机制；失败则保存边界并重新判断方向。

## 数据与公平性

- 同一固定版本Qwen2.5-0.5B，FP32冻结主参数、BF16 autocast，Q/K/V/O rank8 alpha16 LoRA，共1,081,344可训练参数。输出头冻结。
- 每步16384个输入位置和同数目标位置，完整因果上下文。分块输出头每次256个位置，完整反向，无梯度截断。
- 64个训练窗口，固定顺序循环4轮，每条轨迹256更新、4,194,304个目标token。唯一训练目标位置1,048,576；重复学习次数另报。
- calibration用4个已有validation窗口，属于已使用开发数据。
- report预留train语料中的12个16K窗口，排除与已知本项目Qwen训练窗口及本轮训练窗口的位置重叠；有62个候选可选。数据来自同一WikiText版本，并非外部未污染基准，也没有排除旧模型实验中的所有历史接触或预训练污染。只称本轮留出集。
- train-calibration.npz与report.npz独立保存。训练进程不加载report.npz；控制器在9条调参轨迹结束后锁定学习率，3条复跑结束后才启动报告评测。文章主题相似与重复文本不能仅凭位置隔离排除。

## 固定实验表

第一种子2026091560：每种方法学习率3e-5、1e-4、3e-4各一条，共9条256步轨迹。每64步记录calibration。每个方法按第256步calibration均值最低选择学习率，平局选较小学习率；不挑选其他checkpoint，不读取report选参数。

第二种子2026091561：密集/K4/K16分别复跑选中的学习率，共3条。两种子共享训练顺序；仅初始化不同。最后报告三方法两种子的全部6个结果，共3072次科学训练更新。三方法GPU预检另有18次诊断更新，不混入训练结论。

优化器AdamW，betas=(0.9,0.999)、eps=1e-8、weight_decay=0；梯度范数裁剪1。前16步线性warmup，随后线性衰减至基准学习率的10%；全部方法相同。与旧固定学习率试验不是同一协议，旧质量结果不能拼接成这里的结果。

## 指标和停止条件

主指标：最终12窗口NLL，对同种子密集基线逐窗口做差；报告两个种子的全部数据。探索性筛选门槛：两个种子分别都满足平均NLL差不超过0.03 nats且训练时间比不高于0.95。不以这个门槛当统计显著性或论文充分条件。

时间包含数据搬运、前反向、有限值检查、梯度裁剪、优化器和调度器；另报评测/存档/启动在内的进程总时间，单独核算三次学习率搜索，避免只报赢家成本。不同checkpoint的校准曲线用于下一阶段设计；本轮没有证明完全收敛或达到同质量的最短训练时间。

额外报告最后4096个相同目标在完整16K与截断4K上下文下的损失差，观察额外上下文是否还有帮助。短输入位置重新从0开始，且WikiText会跨文章边界；只是上下文敏感性诊断，不当作长距离推理能力基准。它不用于调参。

任何数值、OOM、恢复或运行时错误即停止后续任务并保存失败。每进程上限900秒，整控制器上限7200秒；这是程序时间上限，**不会自动停止RunPod计费**。不自动提高预算、换大卡或试新学习率。

## 数值与断点

CPU检查验证随机训练连续8步与4步存档后恢复的loss、参数、Adam状态和调度器逐位一致，涵盖Python/NumPy/Torch随机状态。此结论只针对CPU小模型。

新GPU和这份新runner仍需现场验证：256 token数学参考、2048 token整块/分块损失梯度、16K未来扰动，以及4步连续对照2步存档恢复的GPU结果。GPU允许参数atol=1e-6/rtol=1e-4、损失差<0.001，失败即停；不承诺GPU逐位一致。每方法GPU预检通过后才可进入正式训练，检查绑定代码/数据配置/扩展SHA与GPU运行环境。

checkpoint包含LoRA参数、优化器、调度器、步数/数据游标、三类CPU随机状态、CUDA随机状态、历史日志与配置身份。原子写入并保存SHA索引；base模型单独按版本和SHA恢复，不把它复制进每个checkpoint。2/64/128/256步存档；中断最多回退到最近存档。继续时使用新的输出目录，拒绝配置/方法/学习率不匹配。内核自身仍可能存在非逐位确定性。

## 租卡边界

本机准备不启动SSH/GPU。下一步确实需要一张CUDA卡来跑新runner的GPU预检。可复用或重启已租的48GB卡，无需多卡或升级80GB。旧48GB卡的16K前反向计时约0.8–1秒/步，仅3072步核心计算粗估约45–55分钟；完整12条训练加加载、评测、存档通常按1–2小时准备，环境恢复时间另算，尚未经新runner实测，不承诺费用。实际花费=控制台每小时价格×运行时间+存储费。

新环境Python3.11、torch2.8.0+cu128及冻结依赖；必须正确加载候选wheel扩展，而非原版。恢复指引见flashmoba-long-cost-stop-and-resume-2026-09-15.md。完整模型在本机；实验增量包和候选wheel已准备，上传后先按manifest核验。

运行方式（在已恢复云项目根目录，候选包已安装且扩展SHA正确）：

```bash
/opt/native-sparse-flashmoba-env-v2/bin/python scripts/run_amp_recovery_stage.py --output results/amp-recovery-stage-v0
```

默认先做三种方法预检，成功才运行冻结的9+3条训练及6次报告评测。只做预检可加--preflight-only；该模式结束后不会自动续跑，需要在保留证据的前提下安排正式控制器。失败不得直接覆盖同名目录重新执行。

```bash
/opt/native-sparse-flashmoba-env-v2/bin/python scripts/analyze_amp_recovery.py --stage results/amp-recovery-stage-v0
```

本轮本机准备不能保证新GPU环境导入成功、16K新数据梯度门槛通过或最终质量提升；这些正是下一次租卡要检验的事项。

## GPU执行修订v1（正式训练前）

新Pod预检发现：不经过存档恢复，完全相同权重的16K反向重复计算也有梯度差（dense约0.8%，K4/K16约0.2%–0.3%相对L2）。显式启用PyTorch确定性算法和稀疏后向deterministic=True后，三方法各3次梯度逐位一致。故全部方法统一启用确定性后向，重新预检；不放宽原断点门槛。旧配置另存config-before-deterministic-v1.json，旧失败不覆盖。新的训练时间必须实测，不直接沿用旧非确定性测速收益。CPU恢复检查仅支持状态实现，不能覆盖GPU算法重复性。
