# 接续节点：需要扩大训练量与上下文，尚未有方法胜出

本地工作已推进到真正的70M主干联合训练，6组全部完成，20项正确性检查通过。两个先前候选（均匀集合外抽查、两块抽样头间归一化）均已关闭；没有以换层、改阈值、反复扫参寻找正结果。

## 为什么当前最小实验不够

从随机初始化训练65,536 tokens后，稠密模型在16段开发集上的NLL为7.29865。保留开头块与最近若干块、同样只看8个完整块时为7.29811；两者几乎重合。但完全不给历史上下文、每个位置仅看当前token时为7.48706。因此模型确实学会利用部分上下文，不能说它“完全没学会”；当前设置对完整的动态全局路由不敏感。

同一套诊断对早期预训练权重则有区分能力：稠密模型完整注意力为4.56783，sink+recent为4.96427，仅当前token为6.87170。这表明不能拿随机起步短跑中几条曲线重合来支持“从头稀疏无损”。对照只能支持这个小设置下的判断，并非证明模型完全没有长程能力。

真实联合训练中的32步预热也没有达到预先固定的0.02 nats门槛：早期权重在测试集追回0.01077，随机权重追回0.00064。不能推广成所有预热都无效；32步不是经过充分训练的官方QSA索引器预热。冷启动、稠密预热等大方向已经被MiniMax Sparse Attention等前作研究，不能当作我们的新贡献。

目前合理的扩大目标是让数据、训练量与评测足以区分路由质量；还没有候选方法值得做论文级扩训。

## 具体下一阶段

1. 保持约70M参数。先扩到2K上下文，完整块大小4，选64块（约256 tokens）并保留尾块；另准备有明确远端依赖的读出。
2. 从稠密控制组开始，用约1M训练tokens检查任务是否已有区分能力。使用新准备的文章级连续序列与固定留出集，不把现在256-token段落直接拼接后冒充长文档。
3. 若稠密模型尚不能在受控评测中利用被稀疏对照删掉的信息，可按预先固定的阶段最多推进到10M tokens；若仍无区分能力，先处理任务设计，停止比较稀疏方法。
4. 稠密控制有效后，再执行第一步稀疏与充分定义的短预热对照。预热充分性及相同token/真实成本口径在开跑前冻结。只有有可操作信号时补独立种子。
5. 关于Qwen的结论还需包含Gated DeltaNet路径的架构验证；当前纯GPTNeoX不能直接替代。实验扩大本身不解决新颖性问题。

按本轮256长度、每组实际CPU训练时间线性换算，10M tokens约需5.24–6.22小时/组；这只扩大token量，**不能当作2K长度的耗时估计**。2K的显存、吞吐和稀疏后端必须实测。扩大仍可分阶段，不能一次开满所有模型、种子和长度。

## 工程准备与费用

已补充真正gather选中KV的可微参考与设备迁移路径，CPU整体前向/反向核验通过。设备短测入口：

```powershell
.\.venv\Scripts\python.exe src\benchmark_joint_device.py --device cpu --length 256 --max-seconds 60 --output logs\另取新名字.json
```

CUDA需要独立兼容运行时，且显式指定 `--device cuda`；无CUDA时会报错，不会回退CPU并声称GPU测试成功。按256、512、1024、2048逐级短测；一次最多4个技术更新，时间上限在步骤间检查，单步不是硬实时中断。该工具不创建云资源，也不会停止云端计费。

gather参考会复制每个query的KV，可能比高效稀疏内核更占显存。它用来验证路径与测量适配风险，不能据此声称GPU加速。正式CUDA训练运行器、2K数据、有效的云连接及账户停机/计费保护还未就绪，当前不启动付费作业。

本项目新增云支出0美元。总上限500美元、首个云阶段30美元保持不变。当前本机RTX5070读取到约5.8GB可用显存；这只是当时快照，没有关闭其他程序，也未假定2K训练能装下。
