# 混合精度与 16K prefill：成本结果和数值诊断

更新：2026-09-15T17:36:17.429509+00:00。

本轮发现有限但可重复的成本空间：同为 BF16 混合精度，K4 的 16K prefill 耗时比稠密少 13.5%–14.4%；8K 前向/反向少 8.4%–9.3%。K16 在这组混合精度设置下更慢。本轮没有参数更新，不能证明质量恢复，也没有建立原创方法贡献。

## 完整模型计时

表中绝对时间是两个计时轮次中位数的均值；节省范围是在同精度、同长度、同轮次内对相应稠密基准计算。每块 3 次预热、10 次计时，第二轮倒序条件。范围不是置信区间，也不是两个训练种子。

| 精度 / 长度 | 工作量 | 稠密 ms | K4 ms | K16 ms | K4 耗时节省范围 |
|---|---|---:|---:|---:|---:|
| FP32 主干 / 8K | prefill | 294.69 | 286.61 | 306.10 | 2.18%–3.28% |
| BF16 混合精度 / 8K | prefill | 95.19 | 93.75 | 119.37 | 1.17%–1.85% |
| BF16 混合精度 / 16K | prefill | 230.94 | 198.73 | 256.22 | 13.51%–14.37% |
| FP32 主干 / 8K | 前向 + 反向 | 868.11 | 826.42 | 862.12 | 4.77%–4.83% |
| BF16 混合精度 / 8K | 前向 + 反向 | 359.37 | 327.48 | 372.66 | 8.42%–9.32% |

![完整模型成本](figures/flashmoba-mixed-cost-v0.png)

Prefill 计算完整输入，生成新的 KV cache，只计算最后一个位置的 logits，未运行 decode。8K 混合精度峰值分配显存约 2.43 GiB，16K 约 2.95 GiB；三种注意力实现的峰值相同。稀疏注意力仍保留完整 K/V cache，没有据此宣称缓存压缩。

前向/反向计算全序列 logits 和 FP32 交叉熵，包含清梯度；不包含优化器更新、输入搬运或梯度检查。它与前轮包含优化器和搬运的完整训练步不是同一计时定义。8K 混合精度峰值分配显存约 27.81–27.98 GiB。

FP32→混合精度的绝对耗时下降不能算作稀疏算法收益。此前较强稀疏在 FP32 小试中仍有明显质量损失；不能把此前质量数字与这次 AMP/16K 时间拼成一个已经验证的质量/成本点。

## 为什么 v0 失败后又出现 v1 / v2

v0 将混合精度下的模型 native eager 当成唯一输出和梯度参考。Flash 稠密与它的 logits 相对差为 2.46%，NLL 差为 0.00717，LoRA 梯度相对差为 28.89%，未通过原门槛，队列按约定停止。这次失败保留，没有改成“通过”。

随后做的 256-token 诊断发现：

- 复刻 native eager 的计算路径后，输出和梯度逐位相同，支持接入过程没有改变其计算语义。
- 固定 BF16 Q/K/V 和 BF16 输出，用 FP32 完成 score、softmax 和加权求和时，Flash 与该参考的全模型梯度差为 6.24%；全块稀疏为 7.63%；native eager 与该参考相差约 25.73%。
- 主动模拟 score 和概率的 BF16 舍入后，与 native eager 的梯度差缩小至 4.42%。只模拟概率舍入没有解释这么多差异。因此 score 等中间值的物化/舍入能解释很大一部分差异，但没有证明它是唯一原因。
- 固定真实首层 Q/K/V 和相同外部梯度后，Flash 与全块稀疏均通过原有 atol=rtol=0.03 的逐元素输出/QKV 梯度参考测试。本机独立 FP64 重算也通过。其 Q 梯度相对 L2 仍约 3.24%，不能称为完全无误差。

基于这些诊断，v1 是另行冻结的探索性成本协议：以同一 BF16 输入/输出的 FP32 数学实现为参考，分别核对 Flash 与全块稀疏，采用 logits <0.02、NLL <0.05、梯度相对 L2 <0.10，并增加实际长度因果检查。它改变了参考和检验结构，不能说仍是原 v0 标准或通过了原先 <0.01 的 dense-vs-sparse 输出门槛。v1 在任何 AMP 耗时结果产生前固定。

8K/16K 的新参考检查通过；实际长度后半段输入扰动不影响前 128 个 hidden states。数学梯度参考只做了 256 token，不是 16K 全模型精确梯度证明。对长期训练轨迹的影响仍需要验证。

详见 [v0 协议](flashmoba-mixed-cost-protocol-2026-09-15.md) 与 [v1 修订依据](flashmoba-mixed-cost-v1-protocol-2026-09-15.md)。v2 只负责下面的 16K prefill 独立续测，具体配置保存在 `configs/flashmoba-mixed-cost-v2.json`。

## 16K 反向显存不足

16K 稠密 prefill 可以运行，但完整反向在预热第一步失败：当时进程使用约 44.46 GiB，剩余约 2.92 GiB，另需分配 9.27 GiB。该失败发生在 dense，因此不能归因为稀疏路由。

该分配量与 16,384 × 151,936 的 FP32 全词表张量大小一致，提示输出层/交叉熵的内存路径值得优先处理；这是由尺寸和错误位置作出的推断，尚未用内存 profiler 精确归因。

v1 按规则停止，没有继续尝试 16K 稀疏反向。随后 v2 在新进程中只测 prefill，重新测齐两轮稠密/K4/K16；不把中断前那一个 dense 时间块混入最终配对结果。16K 的反向与训练质量仍未完成，不能写成训练成功。

## 现在值得做的下一步

暂不换更贵的 GPU。先把全词表输出与交叉熵改成受控的分块计算，或其他经过验证的低显存实现；在短序列核对损失和梯度，再恢复 16K 前向/反向成本测试。这是工程准备，不是新的论文贡献。

随后才适合冻结新的同精度质量恢复实验：配对稠密与 K4，明确相同 token 和相同墙钟两种预算，使用新的最终报告划分，保存优化器状态以便续训。本轮成本优势只说明这个实验有一定计算空间。前轮已观察的报告窗口不能再当作未观察的最终测试。

目前没有扩大长训练，也没有新的质量收益、原创性或论文充分性结论。Qwen2.5-0.5B、LoRA、两个计时轮次、单 GPU/单输入的结果不能直接推广到 Qwen4 或全参数原生稀疏预训练。
